## Ce qui est démontré au-delà de la consigne

- Aucune image ni aucun binaire non vérifié : k3s, images système k3s (airgap), Zot, BuildKit, crane, runner par
  SHA-256 ; image Ubuntu par la signature GPG de `SHA256SUMS` ; image Python par digest ; dépendances par hash.
- Pod Security Admission `restricted` sur `demo` : un pod privilégié est refusé (rapport, section 6).
- Les pull requests ne s'exécutent jamais sur la forge (workflow `pr.yml` sur runner hébergé, sans secret).
- Pas de Docker sur la forge : BuildKit autonome, le runner n'a accès qu'au socket de build (ADR-002).

## Écarts et limites connus

- Le déploiement est lancé par `make deploy` depuis l'hôte, pas par la CI : la CI n'a aucun accès au cluster (pas de
  kubeconfig dans GitHub). Un déploiement continu est envisageable en J4, avec un compte de service limité à `demo`.
- Une seule machine physique (`laptopdlamort`) : le plan de contrôle n'est pas redondant (ADR-001).
